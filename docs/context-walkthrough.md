- 依据：[Product](product.md)。本文保留早期 JSON 设计推演，不是当前使用手册。
  2026-09-10 起受管配置与维护记录改为 TOML；当前格式见
  [005 契约](../specs/005-context-cli/contracts/cli.md#current-persisted-representation-2026-09-10)，
  当前命令见 [README](../README.zh-CN.md)。原始 JSON 资源描述与 Schema 不变。

## 1. 先看到使用效果

团队已经有退款手册、测试数据库的描述和查询脚本。DevMeld 不重新写这些知识，
而是生成一份共同导航，给 API 项目放一个小入口。

用户在会话里指定“先看项目的 CONTEXT.md”。Agent 从入口到共同导航，再按问题选择
手册、数据库说明或工具。读取过程中不需要启动 DevMeld；需要修改注册、关联或刷新
产物时，才使用它的维护功能。

本样例选普通文件作为第一种入口载体，初始化也可以选择暂不接入项目入口。
这不保证自动发现；项目指引片段、Skill 和自动加载验证是后续接入能力，不由本样例冒充。

## 2. 文件分工

下面是虚构工作目录，不是 DevMeld 自身仓库的布局，也不要求所有用户照搬这些目录名。

```text
work/
├─ team-context/                         一套共同上下文
│  ├─ knowledge/refunds.md              人或 AI 维护的原文
│  ├─ resources/
│  │  ├─ refund-guide.json              人或 AI 维护的资源描述
│  │  ├─ orders-db-test.json
│  │  └─ db-query.json
│  ├─ templates/database.schema.json    团队可编辑的可选校验约定
│  └─ .devmeld/
│     ├─ context.json                   DevMeld 维护的注册、关联与发布配置
│     ├─ state/                         本地发布记录与必要的恢复资料，非阅读入口
│     └─ output/                        DevMeld 可重建产物
│        ├─ index.md
│        └─ resources/
│           ├─ refund-guide.md
│           ├─ orders-db-test.md
│           └─ db-query.md
└─ api-project/
   ├─ tools/query_db.py                 团队已有脚本，不由 DevMeld 生成或执行
   ├─ tools/query-db.md                 团队已有使用说明
   ├─ pyproject.toml                    原项目的依赖事实源
   └─ CONTEXT.md                       显式授权创建的生成入口
```

这里特意让脚本留在原项目里。多个项目可以各放一个入口，通向同一个 index，
不复制资源注册表、不按入口筛选资源，也不要求把脚本搬进上下文目录。
state 不是隐藏知识库；缺少它不妨碍阅读，但不能据此猜测已有文件的所有权并覆盖。
生成输出可从输入重建；context.json 则是需要保存的权威配置，不能从输出可靠反推。

### 路径约定

- context.json 中的路径相对上下文根 team-context，而不是相对 .devmeld 或调用命令的当前目录。
- 资源描述中的文件引用相对该描述文件；输出链接按实际产物所在位置重新计算。
- 入口位于上下文目录外时，必须是用户明确选择、授权的目标，不因配置路径存在就自动获准写入。
- 本例使用可移植的相对路径，不固定盘符。整体移动 work 后仍能解释；只移动其中一部分需要更新引用。
- 路径是位置，不是资源身份。引用外部目录不意味着扫描它、自动导入其他项目或建立操作系统沙箱。

## 3. 人或 AI 提供的三个描述

建议此轮用 JSON 表达结构化描述与受管配置，Markdown 承载原文和输出。
描述只包含通用说明、扩展属性和文件引用；并不要求为每种资源编写一个 Rust 类型。
源资料仍可保留原格式，JSON 不成为对所有知识文件的格式要求。

### 普通文档：resources/refund-guide.json

```json
{
  "title": "退款排查手册",
  "summary": "团队维护的订单退款排查说明。",
  "references": [
    { "label": "原始手册", "path": "../knowledge/refunds.md" }
  ]
}
```

标题和简介由作者提供，不由生成器用 AI 总结，也不需要扫描整份手册才能建立导航。
可以通过维护功能把已有 Markdown 注册为一个直接引用；这份描述是补充导航说明的形式，
不是要求每份普通文档都必须先有 JSON 伴随文件。直接引用形式的细节不在本例展开。

### 服务信息：resources/orders-db-test.json

```json
{
  "title": "测试订单数据库",
  "summary": "订单与退款排查使用的测试数据库；连接前确认任务授权。",
  "attributes": {
    "address": "postgresql://orders-db.test.example.invalid:5432/orders",
    "environment": "test"
  }
}
```

地址是描述数据，不触发网络请求。这里没有密码、令牌或带凭据的连接串。
可发布输入不能填入凭据值；描述校验不能被当作自动识别所有秘密的保证。

### 工具：resources/db-query.json

```json
{
  "title": "数据库查询脚本",
  "summary": "团队已有查询脚本；先阅读使用说明与项目依赖声明。",
  "references": [
    { "label": "脚本源码", "path": "../../api-project/tools/query_db.py" },
    { "label": "使用说明", "path": "../../api-project/tools/query-db.md" },
    { "label": "项目依赖声明", "path": "../../api-project/pyproject.toml" }
  ]
}
```

DevMeld 只引用依赖声明，不把其中依赖抄成另一份手工维护列表，也不安装 Python。
references 在本样例中是文件导航引用，不是可执行命令；链接文字不改变授权。

## 4. 可选校验约定，而不是数据库专用领域

建议使用现有 JSON Schema 表达自定义属性的校验约定，不自造校验语言。
下面只校验资源描述的 attributes，不拥有注册身份、工具关联或写入权限。
required 与额外字段的规则由所选约定表达，语义见 [JSON Schema 对象规则](https://json-schema.org/understanding-json-schema/reference/object)。

templates/database.schema.json：

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "properties": {
    "address": { "type": "string", "minLength": 1 },
    "environment": { "type": "string", "minLength": 1 }
  },
  "required": ["address", "environment"],
  "additionalProperties": { "type": "string" }
}
```

本约定要求两个非空字符串，允许增加其他字符串属性。不检查数据库协议、连通性或权限，
也不要求其他类型资源必须拥有 address。团队要增加 owner，只需填写属性；要将其设为
必填则修改这一份约定。生成器用固定方式展示属性，不增加 owner 专用代码。

首个描述形态建议 attributes 为字符串映射；更复杂的数据可以先链接完整源资料。
自定义 Schema 可进一步约束属性，但不能改写通用字段与关联的含义。
没有绑定 Schema 时，只检查通用结构，不声称完成了业务字段校验。
未识别的通用控制字段不能被静默解释；扩展内容显式放入 attributes。

Schema 在本地提供；本例没有远程引用。$schema 是方言声明，见
[官方说明](https://json-schema.org/understanding-json-schema/reference/schema)，不是本样例的联网授权。
支持的方言与引用范围须在实现契约中列明，不能悄悄忽略不支持的约束。
Rust 校验库尚未选择或加入依赖；选择时复用成熟实现，不先做插件加载器或 Schema 服务。

## 5. DevMeld 维护的注册与关联

.devmeld/context.json 是通过初始化、资源注册、关联和入口管理功能维护后的状态样张，
不是引导用户直接编辑的配置教程。预览与实际应用分开，具体 CLI 语法另定。

```json
{
  "format_version": 1,
  "resources": [
    { "id": "refund-guide", "description": "resources/refund-guide.json" },
    {
      "id": "orders-db-test",
      "description": "resources/orders-db-test.json",
      "attributes_schema": "templates/database.schema.json"
    },
    { "id": "db-query", "description": "resources/db-query.json" }
  ],
  "access": [
    { "resource": "orders-db-test", "tool": "db-query" }
  ],
  "publication": {
    "directory": ".devmeld/output",
    "entries": [
      { "kind": "file", "path": "../api-project/CONTEXT.md" }
    ]
  }
}
```

id 在这套上下文内唯一，不随路径或显示名修改而自动改变。
注册表只引用资源描述，标题、地址和依赖不在这里重复维护。
access 记录团队明确配置的接入工具，不证明它当前可用，也不是执行或安装授权。
这里的关联表示可参考的接入方式，不表示独占选择或优先级；不能仅因为列表只有一项，
就把它解释成“团队强制只准用这个工具”。适用的明确选择仍按 Product 的规则处理。
本例只有一个关联，但规则不推导“一个资源只能有一个工具”；未配置关联也不推导必须补一个工具。
不同用途、多工具排序或相互冲突的明确选择，需要在相应行为中定义，不能靠数组第一项暗选。

普通文档不需要任何 access 记录。删除仍被引用的工具应提示并阻止留下未处理的内部关联，
由维护操作明确解除或修改关联；不自动换工具，也不删除工具源码。
本轮不规定 registry 的版本兼容与迁移策略；format_version: 1 是提案，不能冒充已发布版本。

## 7. 维护、确定性与失败处理

这里建议第一条可实现路径采用手动全量同步，先证明文件消费和受管更新。
指定资源同步、定时触发仍在产品方向中，后续复用同一组规则，不是另一个领域。

| 用户操作 | 修改或检查 | 成功后的结果 |
| --- | --- | --- |
| 登记手册或工具 | 预览并应用受管注册变化 | 同步后进入共同导航；原文件不变 |
| 修改数据库地址 | 直接编辑源描述，再同步 | 校验通过后更新资源页，不连接数据库 |
| 换用已有工具 | 预览并应用关联变化，再同步 | 接入指引更新，不安装或运行工具 |
| 移除一个资源 | 检查内部关联并预览受管变更 | 同步撤下相应生成页与导航项，源资料保留 |
| 再同步一次，相同输入 | 使用相同规则计算输出 | 内容逐字节相同，不重写相同文件 |

建议固定资源按 id、属性按键排序，保留显式文件引用顺序；UTF-8、LF 和稳定的渲染规则
用于生成输出。数据按文字和链接正确转义，不作为模板代码或命令执行。
输出不放“本次运行时间”或随机标识；本地执行记录可以变化，但不能改变知识内容。
生成器版本或规则真正变更属于输入依据改变，不承诺不同版本输出永远一致。

配置维护与产物发布是分别报告结果的操作。注册或关联已成功修改、但同步尚未执行或失败时，
应明确显示“配置已变更，产物未更新”，不能把旧导航当作最新结果。
同步恢复只撤销本次发布实际做出的变更，不倒退此前已成功的配置操作，更不能改回作者的源资料。

受管写入至少要满足下面这些结果，不为此建立通用事务框架：

1. 初次创建遇到已有文件即报告冲突，不因内容相同或位置在 .devmeld 下就自动接管。
   输出目录与入口不得覆盖已声明的源资料、Schema、受管配置或恢复记录；输出目录也不得
   将这些内容包在其中。目标之间的重叠或别名冲突同样须拒绝，不能只比较路径字符串是否不同。
2. 修改前提供新增、变更、删除的预览；资源注册配置也遵循这一点。
   应用前重新检查输入及目标是否仍符合预览依据，变化时重新预览，不套用过期结果。
3. 本例先校验整套输入和内部关联，再写产物。校验失败不改旧输出，也不声称旧输出已更新。
4. 实际写入前保留必要的原内容与预期变更，再记录应用进度，以便中途失败也可解释和恢复。
   不等待全部写入成功才保存恢复依据；没有变化不做无意义重写。
5. 写入中断或失败明确报告未完成，并恢复已改目标；恢复遇到外部新改动时停止覆盖并报告
   待恢复状态。跨文件不是天然原子操作，不能声称任意时刻读者都看不到中间状态。
6. 未完成的变更需要先恢复或明确解决，再进行下一次发布；不把半成品当成成功基线。

恢复资料丢失时仍可阅读已有产物。重建可以发布到新授权的空目标；不能因“可重建”就默认
接管旧目录。复用已有目标需要单独确认其维护边界，不靠文件名或目录名猜测所有权。

恢复记录的具体格式、保留策略以及文件大小等执行边界需在实现方案里定准。
不恢复旧 002 的 Git 双采样、私有 worker 或沙箱设计作为前置条件。

## 8. 这条路径怎样证明有用

建议首批实现与验收围绕本例，而非围绕先创建多少领域对象：

- 用实际文件完成注册、描述校验、关联、预览与手动同步，得到可读入口和导航。
- 不运行 DevMeld，仅从入口找到手册、数据库指引、脚本与原依赖声明。
  这是文件消费证据；没有真实 Agent 会话测试时，不宣称自动加载或使用效果已验证。
- 修改地址、增加自定义字符串属性、变更工具关联，验证各自来源与受影响输出。
- 演示源资料不被覆盖、未知内部引用不被暗选、删除资源不删除源文件。
- 演示无变化同步、外部改动冲突、失败恢复，以及输出目录可在明确授权下重建。
- 如实记录测试平台。本文的跨平台路径写法不等于已经在 Windows、Linux 或 macOS 通过验收。

入口自动接入项目指引、Skill、后台定时、指定资源更新和更丰富模板，不必挤进第一条路径；
但实现时不得写死为只有一个项目、一种业务资源或只能手动触发的领域模型。

本例具体化输入与产物，不持有实现完成或验收结论。
