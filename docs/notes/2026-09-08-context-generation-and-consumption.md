## 一句话模型

DevMeld 按用户配置整理、生成并更新磁盘上的上下文产物；Agent 接收用户问题，
通过暴露的入口和导航自行选择、读取资源，不必每次向 DevMeld 请求上下文。

## 已确认的方向

### 1. 生成和使用是两个阶段

- 生成阶段：用户维护实际资料与配置，DevMeld 根据明确输入和规则生成上下文产物。
- 使用阶段：Agent 听到用户问题，读取入口、导航和需要的原始资料，决定使用哪些资源。
- 管理阶段：人或 Agent 需要调整 DevMeld 自己维护的状态、生成或刷新产物时，
  调用 DevMeld 的相应功能。这不等于每次读取资料都必须调用它。

正常读取依赖的是磁盘内容，不是一直在线的 DevMeld 进程。关闭 DevMeld 后，
已经生成且其引用目标仍可访问的内容应继续可读；只是不会凭空得到新的更新。
这不是降级读取，而是预期的正常使用方式。不要求每次提问都启动服务、调用 CLI、
走查询接口或把自然语言问题转交给 DevMeld。

已确认提供可选、可配置的更新机制，包括手动指定资源更新和后台定时更新；
具体配置与调度实现尚未决定，见第 7 节。
这也不排斥未来可选的运行时辅助能力，但不能把它重新设为正常阅读的前提。

### 2. 索引对象、受管状态与生成产物必须分清

| 内容 | 谁负责维护 | 人或 Agent 如何修改 |
| --- | --- | --- |
| 人或 AI 编写的知识、笔记、工具脚本等原始资源 | 原始内容的所有者 | 按其项目规则与授权修改；DevMeld 可以索引或引用 |
| 明确由 DevMeld 管理的声明、配置、关系等状态 | DevMeld 的管理机制 | 调用相应 DevMeld 功能，不绕过机制直接改受管状态 |
| DevMeld 生成的导航、索引、入口或分发副本 | DevMeld 的生成机制 | 修改拥有该事实的输入或生成规则，然后重新生成 |

具体哪些文件属于第二类，仍需后续定义，不能凭目录名称判断所有权。
“被 DevMeld 索引”不等于“内容由 DevMeld 拥有”，也不意味着 Agent 不能写它。
反过来，不能因为 Agent 可以写知识，就允许它直接修改 DevMeld 的生成产物。
同一份内容若被分发，应分清可编辑源与生成副本，避免多个手工维护的事实源。

无法百分百阻止人或 Agent 改文件。需要通过清晰标识、维护说明和提示词引导：
哪里能编辑、哪里是生成结果、应修改哪个源、何时需要调用 DevMeld 的机制。
这里不要求增加复杂的权限框架或操作系统级强制隔离。

### 3. 生成结果不应无故漂移

在输入事实、配置、模板或扩展规则、生成器版本均不变的条件下，
DevMeld 的生成结果应保持一致。一次刷新不是让 AI 重新发挥、改写知识的机会。

AI 可以帮助用户编写或修改输入；明确输入形成之后，生成过程仍应按确定规则运行。
原始事实真的改变时，产物当然可以更新。Agent 的使用行为需要改进时，应调整其行为；
生成逻辑需要改变时，应修改受支持的规则、扩展或 DevMeld 源码，而不是手改生成结果。

字节级一致性的验证方式、运行日志、时间戳和无变化时的写入策略尚未设计。
这些实现细节不能反过来制造无意义的知识变化。

### 4. 团队通过模板和扩展提供实际内容

DevMeld 应提供合理的扩展机制，让不同团队决定自己的资源、配置、工具和生成方式，
而不是把某个团队的业务或某种语言写死在产品里。

- 可以提供大部分团队常用的可选资源模板，帮助初始化和说明如何填写。
- 模板提供结构、说明和示例，不替用户编造真实的仓库、环境、工具或业务事实。
- 实际信息由用户添加；人和 AI 都可以在规则允许的范围内帮助维护和扩展。
- 提供良好的说明、示例和维护提示词，让扩展可理解，也说明受管内容的修改机制。
- 生成时依据这一套 DevMeld 配置的资源和关联，不依赖 DevMeld 听到当前用户问题，
  也不额外按项目入口筛选资源，见第 8 节。
- 使用时暴露导航，由 Agent 决定此次需要读取或使用哪些内容。

例如，团队 A 可以提供订单仓库、退款知识和查询脚本，团队 B 可以提供前端仓库、
组件文档和截图工具。机制可以共用，真实资料和组合由各团队提供。
这些只是例子，不是已经冻结的内置模板清单。

“可扩展”不自动等于“必须支持任意可执行插件”。具体扩展协议、类型、校验和
呈现方式仍需设计；描述资源与增加处理能力的边界已进一步确认如下。

#### 4.1 描述扩展与处理能力扩展分开

Maintainer 已确认：新增资源描述通常不需要修改 DevMeld 代码；新增自动处理能力
才可能需要代码扩展。DevMeld 可以把一种资源组织清楚，而不必具备操作它的能力。

团队可以通过模板和配置描述资源的用途、环境、关联项目、说明位置及推荐工具等信息，
人和 AI 都可以帮助填写。DevMeld 按约定结构校验并生成导航，不必为每一种资源新增
专用领域模型。这些信息项是例子，不是已冻结的必填字段或 Schema。

例如，“测试数据库”的连接说明和工具使用指引可以作为资源描述进入导航，
由 Agent 按任务和授权使用。若要求 DevMeld 自动连接数据库、读取表结构并生成说明，
则是在增加采集和处理能力，须另行设计连接、凭据、依赖和失败处理。
配置中的一段文字不会自动赋予 DevMeld 新能力或执行授权。

本次确认的是这条扩展边界，不是连接器、安装器、可执行插件接口或本期实现的批准。

#### 4.2 资源事实由人或 AI 维护，面向 Agent 的接入组织由 DevMeld 维护

Maintainer 进一步明确：资源本身可以由人或 AI 填写，DevMeld 的职责是把资源
提供给 Agent 使用，索引是可采用的方式，不应提前将所有交付形式锁死为索引。

例如，服务的链接信息、用途和环境等描述属于人或 AI 维护的输入。
对于标准化资源，可以约定格式，由 DevMeld 校验；不要求所有自定义资源都采用
同一套强类型结构。格式校验不等于验证服务连通、凭据有效或工具当前可用。

“如何连接这些服务”的面向 Agent 的组织与指引由 DevMeld 负责：
不只是列出服务地址，还要根据明确的配置和规则，组织资源到接入方式、工具及使用说明
的关联，并以索引等产物暴露给 Agent。团队可以提供工具、脚本、说明及相关配置作为输入；
DevMeld 维护对外生成的接入指引，不能让 Agent 手改生成索引来改变接入规则。
具体关联声明的格式及哪些状态须通过 DevMeld 功能修改，仍待设计。

结合已确认的文件消费方式，这里的“控制”指接入规则的组织与产物维护，
不意味着 DevMeld 必须常驻、代替 Agent 连接服务，或强制拦截所有工具调用。
实际执行仍由 Agent 或相应工具承担；已有明确工具选择不被静默替换，
提供索引也不增加安装、执行或修改环境的权限。工具源文件不会仅因被引用就转归 DevMeld。

### 5. 入口、导航和原始内容各司其职

Maintainer 明确：不能假设 Agent 一开始就知道项目里有 DevMeld 提供的上下文，
也不要求先认识或调用 DevMeld 才能阅读。入口首先是项目自己的小索引，
不是 DevMeld 的产品介绍、进程或 API 地址。

DevMeld 初始化时应提供选项，在项目中创建或接入入口。可选载体包括：

- 在项目指引文件（例如 `AGENTS.md`）中加入一条引用或小段入口内容。
- 通过一个 Skill 提供入口。
- 生成一个普通入口文件，由用户指定给 Agent，或经已有指引引用。

这些是可选方式，不要求同时创建，也没有决定统一文件名或具体客户端协议。
仅维护用户选择并授权的入口范围，不因此接管已有项目指引的全部内容。

在实际会话中，Agent 可以通过所选接入方式在开始时读取入口，也可以由用户指定入口。
不能仅因生成了普通文件，就声称任意 Agent 会自动读取它。通用上下文应能从这个小索引
沿引用一步步找到，不需要 Agent 预先知道所有路径、把全部内容一次性读入，
或在每一步调用 DevMeld。导航层数和目录布局仍未确定。

- 入口负责提供第一步可读的索引及后续阅读方向。
- 导航告诉 Agent 有哪些资源、在哪里、用途是什么，以及已声明或有依据的关联。
- 具体知识、工具代码和完整说明留在其原始资源中，按需读取，不全部塞入入口。

上下文可以包含项目地图、项目知识和使用指引；这些是内容职责，不是已定的文件夹结构。
项目地图帮助找到仓库、资料和工具；知识承载业务规则、流程、决策与经验及其来源。
不必等完整知识库建立之后才有价值，也不要求初始化时由内置 AI 分析完整项目。

正常阅读不依赖 DevMeld 身份认知，与受管产物标明维护来源和修改机制并不矛盾。
具体客户端如何接入、何时加载入口，以及生成内容如何更新，仍需分别设计和验证。
导航不意味着把全部资源一次性加载进提示词，资源可见也不等于有执行或安装权限。

### 6. 工具本体不是导航内容

已有系统工具留在其安装位置；项目脚本可留在所属仓库；共享工具或 Skill 可以有独立来源。
工具本体、使用说明和导航中的引用应分清，不要求把所有工具搬入一个统一目录。

Agent 根据任务读取说明并使用工具，不要求通过 DevMeld 充当执行代理。
不依赖 DevMeld 常驻，不意味着工具自身没有运行环境或依赖。
索引里出现某个工具，不授权安装、执行或修改环境。
工具源与生成副本仍遵循上面的所有权规则，本次讨论不授权实现安装器或执行器。

### 7. 更新机制可配置，资源增删通过同步更新索引

Maintainer 明确：更新不应只固定为一种方式，应提供可选机制，例如通过配置启用
后台定时更新，或手动指定某些资源进行更新。

需区分两个维度：何时触发同步，以及本次更新哪些资源。手动和定时是触发方式，
指定资源是范围选择；它们应遵循同一套生成、校验与所有权规则，而不是产生不同语义。
具体的范围表达方式、配置格式、默认值和调度方式尚未确定。

新增或移除资源后，需要执行同步，使索引反映当前资源集合；不能只改变源资源，
却把旧索引当作已经更新。指定范围更新时，也须保持受影响索引与生成指引的一致性。
这不等于已决定采用文件监听、变化后立即同步、每次全量重建或精细增量算法。
同步移除索引条目不等于授权删除原始资源。

后台定时更新是可选的内容维护机制，不是 Agent 阅读内容的前提。它未运行时，
已生成内容仍可读取，但不能假定已反映后续变化。手动更新也不必以后台任务运行作为前提。
同步不改变原始知识的维护归属，也不授权为刷新而擅自改写人或 AI 的源知识。

此处确认产品方向，不意味着在 002 中立即实现全部触发方式或后台服务。

### 8. 一套 DevMeld 内资源放一起，需要分开时定义两套

Maintainer 明确要求先保持简单：若多个项目的资源需要共同使用，就放在同一套
DevMeld 的上下文中；若确实需要隔离，则定义两套 DevMeld。

同一套 DevMeld 中，资源通过共同的导航组织，Agent 按任务决定读取哪些内容。
不引入按项目或按入口配置资源可见性的额外筛选层，也不为这种筛选增加 Profile、
共享分组继承或跨入口分发规则。新增资源纳入该套配置并同步后，更新共同索引即可。
入口的不同载体只是到达上下文的方式，不因此产生不同的资源集合。

此前助手提出“共享资源由各项目入口分别配置引用，新增资源不进入其他入口”的建议
未被采纳，不应继续作为下一步待确认方案或实现依据。

这里将“两套 DevMeld”理解为两套分别管理的配置与上下文，不是两个必需常驻的进程。
“放一起”是共同组织资源，不要求把所有原始文件搬到同一个目录；具体目录和命名仍待设计。
分开配置与上下文也不代表已建立操作系统级的访问隔离。
旧 Workspace、Context Profile 等概念不再是必须兼容的前提，
其原有领域代码已在后续获准的重置中删除；新概念只按当前规则的实际需要建立。

## 不要在后续会话中重新混淆

- 是 Agent 听问题、选择资源，不是 DevMeld 接收每个问题再决定要给什么上下文。
- 刷新派生产物不等于重新裁定、改写所有业务知识。
- Agent 可以写其有权维护的源知识；不能因此直接改 DevMeld 的生成结果。
- 磁盘位置、扫描发现、逻辑关联、纳入规则、使用权限是不同问题。
- 不能把一切资料都复制进 DevMeld，再让它成为原始内容的唯一访问入口。
- “每个任务创建 Profile”或“关联图自动递归纳入所有资源”不是本轮已确认的方案。
- 独立文件阅读是正常路径，不是 DevMeld 进程不可用时才提供的补救措施。
- 入口由初始化选项显式接入项目，不能假定 Agent 天然知道 DevMeld 或自动发现任意文件。
- 一套 DevMeld 内先共同组织资源；不要再次默认引入按项目或入口筛选资源的配置层。

## 尚未决定

1. 扩展的最小契约：资源如何描述、引用、关联、校验和进入生成结果。
   不提前冻结字段、Schema 或插件框架。
2. 资源组织边界：已确认一套 DevMeld 内放一起，需要分开时定义两套。
   其配置和目录表达仍待设计；已有领域概念需重新论证，而不是作为必须兼容的前提。
   按项目入口筛选不再是待定方案。
   资源发现方式尚未选择，不能从共同导航推导出自动扫描所有目录。
3. 文件布局与所有权：入口和导航放哪里，哪些声明通过 DevMeld 管理，如何引用共享来源。
4. 更新与时效：已确认可配置的手动指定资源更新、后台定时更新及增删资源后的索引同步。
   配置格式、调度方式、默认策略、增量范围、失败和冲突处理及旧产物的时效表达仍待设计。
   落盘不代表永远新鲜，更新索引也不自动证明原有知识仍然正确。
5. Agent 接入：已确认初始化时选择项目入口形式，会话开始读取或由用户指定，
   再沿索引逐步找到通用上下文。具体载体实现、文件名、加载机制及兼容性验证仍待设计。
6. 知识维护：源知识的评审、有效性和更新流程，哪些需要 DevMeld 功能参与。
7. 下一 Feature 的范围与验收：如何从当前基础走到实际的生成与文件消费链路。

## 与现有文档及实现的关系

001 的三个 Core Domain 基础曾按旧要求完成验收；Maintainer 现已要求重新审视它们，
不再默认把三个领域、已有 API 或旧测试当成新设计必须保留的约束。
是否以及如何复用身份、来源、路径等局部能力，要由新模型的实际需要证明。
这不是直接批准实现旧 Managed Materialization、Capability Integration 或新的公开协议。

已删除的旧 002 Spec 和 Plan 描述的是读取声明、观察 Git、调用领域规则并输出
人工检查报告的只读链路，没有覆盖本轮完整的持久化生成与消费方向。
旧检查入口不能解释为最终 Agent 每次获取上下文的必经通道。

先前“调整旧 002、默认保留 001”的推进建议已被否定。应从本轮产品意图重新设计基础和
交付范围，旧 002 的 worker、双采样或其他技术选择没有继承优先权。
旧模型与代码已按获准范围删除；新的领域草案尚未批准，不生成实现任务，不开始新实现。
