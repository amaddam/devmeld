# DevMeld 领域设计草案

- 状态：Maintainer 已同意按此方向继续细化；具体格式、实现范围和 crate 布局尚未批准。
- 依据：[Product](product.md)；不继承旧 001 的领域数量、包名、API 或完成状态。
- 本轮建议：两个领域边界，接入指引作为资源组织内部的规则模块。
- 本稿明确事实归属与变化边界，不创建代码、公共协议或新的 Feature 编号。

## 1. 建模起点与划分结论

DevMeld 组织团队提供的资源，生成并维护可独立阅读的上下文产物。
Agent 接收问题，通过入口与导航自行选择资源。生成器不接收每个问题，也不替
未来的会话预先决定使用哪个资源或执行哪个工具。

一套上下文共同组织一组资源，可以跨多个项目；需要分开时建立两套上下文。
这是配置与资源归属的边界，不是新的 Profile、权限系统或必需的常驻进程。

建议划分如下：

| 领域 | 核心问题 | 拥有的规则 | 不拥有 |
| --- | --- | --- | --- |
| 资源组织（Resource Organization） | 有哪些资源，它们是什么，如何找到和使用？ | 纳入与引用、描述约定、资源关联、接入指引语义 | 源知识的业务正确性、输出文件位置、实际工具执行 |
| 上下文发布（Context Publication） | 怎样将这些信息交付成可持续维护的磁盘内容？ | 入口与导航、生成内容的来源对应、受管写入边界、更新与冲突规则 | 资源事实本身、接入策略、Agent 当前任务 |

这不是“读取领域 + 写入领域”。资源组织有引用与接入语义，发布有独立的产物所有权
与更新规则；二者改变的原因不同。同步是协调这些规则的用例，不再成为第三个领域。

上一版单列的“接入指引”保留明确模块边界，但先归入资源组织：
目前它主要解释资源之间的使用关系，与资源注册、引用校验一起变化，没有独立的
安装、执行或环境管理生命周期。尚不足以为此建立第三套领域对象和持久化体系。
未来若确实形成独立复杂规则，可以再拆；两个领域也不意味着现在必须建立两个 crate。

## 2. 资源组织：先把“是什么、在哪里、怎么用”说清楚

### 最小概念与事实归属

| 概念 | 含义与维护来源 |
| --- | --- |
| 资源引用 | 在本套上下文中指向同一项资源；不把展示名称或本机路径当作身份 |
| 资源描述 | 人或 AI 维护的用途、说明、地址、环境等事实，或者对已有文档的引用 |
| 描述约定 | 团队选用或扩展的格式、字段含义与校验规则；只解释对应资源类型 |
| 资源关联 | 明确声明的资源关系，例如“该服务使用这份接入说明和这个工具” |
| 接入指引规则 | 怎样解释关联、表达使用前提、尊重明确选择并引导复用已有工具 |

这些是建模词汇，不是必须一一实现的类、表或必填字段。
资源可以直接指向普通文档，不要求先填写一整套服务字段。
源内容、资源注册引用、校验结果是不同事实；不会把整份源知识复制到注册状态里再维护一次。

这里进一步提出一项具体的受管边界，供本轮评审：

- 源文档、服务描述、脚本、使用说明、团队模板和描述约定，仍由人或 AI 按其规则编辑。
- “哪些资源纳入这一套上下文”“注册引用指向哪个来源”“哪项服务关联哪个工具或说明”
  作为 DevMeld 受管状态，通过其相应功能调整。
- 原始说明可以解释工具的用法；结构化的资源关联只有一处权威声明，
  不再在描述文件、注册状态和生成索引中分别手工维护三份。
- 校验与指引结果是派生事实，不成为另一份可编辑的注册清单。

逻辑上的权威归属不要求一个数据库，也没有决定必须一个集中配置文件。
身份表示、相对路径如何解析、可移植来源与本机位置如何映射，留给具体输入契约。
保持资源引用不随搬家而改变，不等于现在重建旧 Repository / Checkout 模型。

### 资源与关联的规则

- 纳入资源需要明确的配置或管理操作。不扫描整台机器，不沿链接递归收编所有目标。
- 一个来源可被多处引用，不因出现在多个导航位置就复制成多份资源事实。
- 内部资源关联应能找到其目标；无法解释的引用应指出来源和原因，不静默换成相似资源。
- 移除工具资源时，不能把仍引用它的服务自动改用另一工具，也不能顺带删除服务。
  应暴露受影响关联，由维护机制明确处理。
- 外部地址或普通文档链接不一定要注册为另一项资源；声明含义决定它是来源还是内部关联。
- 标准化描述按所选约定校验；没有专用约定的资源仍可作为通用描述或文档引用组织，
  但不能声称其未知字段已经得到专用语义校验。
- 格式正确不等于服务可达、凭据有效或工具可调用；不建立所有资源共用的 Ready 状态。

### 接入指引不是执行器，也不是会话路由器

普通文档的使用方式可以只是“沿链接阅读”，不强迫每个资源都拥有连接工具。
服务资源可以关联多个用途不同的工具与说明；一个工具也可以被多个服务复用。
工具本体仍在原仓库或安装位置，接入指引模块解释关联与使用规则，不拥有工具源码。
资源到工具的关联本身不等于独占选择、排序或执行授权；适用的明确选择须有相应声明依据，
不能只因关联里恰好有一个工具，就把它提升为不可替代的团队规则。

生成阶段组织项目明确声明的选择、候选方案、使用前提与维护说明。
[Product 的工具指导规则](product.md#tool-and-dependency-guidance)由这里解释，
而不是散落在 Markdown 模板或命令入口中。尤其区分：

- 已声明采用某工具，可以生成该声明及其依据；不能据此写成“当前可用”。
- 若有环境观察，只能说明其来源、范围与时效；过去验证不能保证未来会话仍然可用。
- 没有当前任务证据时，发布条件与待确认事项，不为了填满结果自动探测或安装。
- Agent 在使用时结合当前任务与授权作选择；用户在会话里提出的临时要求，
  不会反过来成为 DevMeld 已经知道的生成输入，也不应自动改写团队配置。
- 明确选择不等于安装或修改环境的授权；现有项目方案与合格本地工具的复用顺序不变。

因此不会建立“DevMeld 收到问题 → 在线挑选工具 → 代为连接”的必经链路。
这里交付的是可阅读、可追溯的指引，不宣称能强制约束 Agent。

## 3. 上下文发布：拥有产物，不重新拥有资源

### 发布维护什么

| 对象 | 职责 |
| --- | --- |
| 项目入口 | 把读者引向这一套上下文；只维护用户授权的文件或片段 |
| 导航与资源指引 | 说明有哪些资源、用途、来源与使用方式，支持按需继续阅读 |
| 产物来源对应 | 说明哪些内容是生成的、来自哪里、应如何正确修改和更新 |
| 发布维护记录 | 支持识别受管范围、已有结果与冲突；不是新的资源事实源 |

这同样不是四套必需实体或独立存储。
文件渲染与入口载体是适配细节；哪些内容可写、哪些属于生成结果，是发布领域规则。
资源组织解释“为什么关联这个工具”，发布只负责将解释忠实交付，不重新选择工具。

### 发布边界与更新规则

- 不同入口载体通向同一套资源导航，不因选择 Skill 或项目指引片段而创建资源子集。
- 初始化只接入选定且授权的范围；已有指引文件不因接入而整体归 DevMeld 所有。
- 生成内容标明维护边界、源位置与正确修改方式，避免读者把产物当作编辑入口。
- 资源增删或关联变化后，同步维护受影响的导航、指引和引用。
  指定一个资源更新不等于只准改一个文件，也不要求采用复杂增量依赖图。
- 撤下资源的生成条目，不授权删除原文档、脚本或工具。
- 遇到非受管内容或产物被外部改动，不静默覆盖、吸收为输入或扩大写入范围。
  冲突与失败不能报告为成功；具体预览、恢复与跨文件失败协议在实现前确定。
- 相同输入事实、配置、规则及生成器版本产生相同内容。
  本次执行的日志与时间不混入知识正文，避免无变化同步制造内容漂移。
  与资源有关的观察时间属于输入事实，可以在指引中如实呈现，不因此省略时效依据。
- 校验结果、接入说明等语义在写文件前已经明确，不能靠渲染模板暗中补业务决定。

### 文件可读，不等于所有来源都被冻结

导航中的标题、摘要或指引是本次生成的派生内容；指向原文件的链接仍指向由其所有者
维护的来源。源文档直接修改后，读者可能先读到新原文，而索引中的旧摘要尚未同步。
要复制内容时，应明确它是生成副本，不能声称链接与副本总是同一时刻的快照。

关闭 DevMeld 不影响已有入口和产物的阅读；来源本身仍需可访问，外部服务也不会因此
变成离线可用。这里不引入原子知识快照、所有源文件副本或实时观察保证。

## 4. 团队扩展放在哪里

| 扩展需要 | 归属与边界 |
| --- | --- |
| 增加“测试数据库”“发布手册”等描述类型 | 资源组织解释约定；模板提供填写说明、示例与校验要求 |
| 为资源补充已有工具和操作说明 | 资源组织维护明确关联与接入语义，不执行说明中的命令 |
| 调整资源在导航中的呈现 | 发布侧呈现规则与渲染适配，不在模板中悄悄改变纳入或授权规则 |
| 增加自动采集、解析或转换能力 | 另行设计边界适配与授权，不能仅靠新增一个类型名获得执行能力 |
| 增加入口载体 | 发布侧接入适配，不增加一套资源选择逻辑 |

例如，新增数据库描述可以校验地址、环境等约定字段并引用团队维护的脚本，
不需要 DevMeld 具备数据库驱动。脚本里出现 Python、JavaScript 或 curl，
也不会要求 DevMeld 安装对应运行时。

只做描述扩展时，不在核心代码里堆积“如果是数据库……如果是某团队……”分支。
另一方面，不为避免任何未来代码修改而预建任意代码插件、动态模块加载器或包管理系统。
具体可配置的校验与渲染能力必须有清晰契约；未支持的处理不能伪装成已经可扩展。

## 5. 用三类资源检验这个模型

以下是逻辑样例，不是已冻结的目录、配置格式、命令或已经执行的测试。

| 资源 | 团队提供 | DevMeld 组织与生成 | Agent 使用时 |
| --- | --- | --- | --- |
| 退款排查手册 | 一份现有 Markdown、用途说明 | 注册来源，生成导航与维护来源指引 | 沿链接读原文，需要修改时按源文件规则处理 |
| 测试订单数据库 | 地址、环境、用途等描述 | 按约定校验描述，关联连接说明与工具，生成资源指引 | 读说明，结合当前授权决定是否连接 |
| 数据库查询脚本 | 仓库中的脚本、依赖声明与使用说明 | 索引脚本来源，在服务指引中复用其引用，不复制依赖清单 | 检查当前环境与授权后使用；不手改生成指引 |

假设三项都已明确纳入同一套上下文，消费路径可以是：

```text
项目入口 → 共同导航
              ├─ 退款排查手册 → 原 Markdown
              ├─ 测试订单数据库 → 资源说明 → 查询脚本与使用说明
              └─ 查询脚本 → 原脚本、项目依赖声明与使用说明
```

生成器不用理解“用户现在是不是在排查退款”就可以准备这些内容。
脚本可同时出现在导航与服务指引中，但只有一处注册引用和一份源脚本，不变成两份维护对象。

再用变化检查边界：

| 变化 | 应改哪里 | 不应发生什么 |
| --- | --- | --- |
| 手册正文修改 | 人或 AI 修改原文；同步更新引用该内容的派生产物 | DevMeld 重写原文或要求所有笔记走审核状态机 |
| 数据库地址变化 | 修改源描述，重新校验并同步 | 修改生成指引来掩盖源描述仍是旧地址 |
| 数据库改用另一个已有工具 | 通过维护机制调整关联，再生成指引 | 静默安装或执行新工具，复制一套依赖清单 |
| 脚本实现更新，引用位置与描述未变 | 修改原脚本；按产物实际使用的输入判断是否需要更新 | 因每次脚本提交而无条件改写全部导航 |
| 被服务引用的工具被移除 | 资源组织指出受影响关联，明确处理后同步 | 自动挑选替代工具或删除源脚本 |
| 入口从普通文件改为项目指引片段 | 发布侧改变获授权的接入方式 | 重建资源事实或改变可见资源集合 |
| 手动触发改成定时触发 | 改同步触发配置 | 更换生成规则或要求读者依赖后台进程 |
| 手改生成的服务指引 | 发布侧识别冲突并提示正确维护路径 | 把改动自动吸收为团队事实 |

## 6. 领域之外：协调与技术适配

同步协调取得明确输入，调用资源组织规则，取得准备发布的事实，再请求发布与汇总结果。
两个领域不互相修改内部状态：语义错误由资源组织解释，输出冲突由发布解释，
跨边界调用由协调承担。它不是一个拥有全部判断的 SyncService。

手动、定时及未来其他触发方式调用同一同步行为。调度器只负责何时触发，
不成为 Scheduler 领域，不先决定后台框架、异步运行时或任务队列。

文件读取、格式解析、Markdown 渲染、入口片段定位以及未来的环境观察是技术适配。
领域规则接收明确事实，不依赖文件格式、特定 Agent、Git 库或系统命令。
传递的事实先是内部协作边界，不因此冻结公共协议或强制使用事件总线。

## 7. 这一轮定什么，不定什么

本轮提交评审的是：两个领域的所有权、接入指引先内聚于资源组织、受管注册与关联的
修改边界，以及上面的三类资源和变化样例。不是两个空包加一批通用对象的建设任务。

暂不引入独立的 Knowledge、Git、Tool Execution、Extension Manager 或 Scheduler 领域；
不恢复 Profile、任务级 Active Checkout 或 query-time Scope Match 作为全局前置条件。
资源来源与局部观察若有真实需要，再在对应场景建模。

当前继续把同一组样例具体化为[输入与生成结果的对照](context-walkthrough.md)：
明确最小描述与关联格式、第一种入口、输出位置和受管修改方式，
并补齐同步失败、冲突与恢复约定。随后再确定首批实现与测试范围。
不用先生成覆盖全部未来能力的 contracts、计划和任务。
领域先行指先确定规则归属，并非先造齐未来所有内存对象。

当前仍是设计阶段。Rust 与已有工程约束保留，但这里不批准新代码、crate 布局或交付验收。
